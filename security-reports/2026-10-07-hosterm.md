# White-box Security Review — hosterm (Tauri v2 SSH client)

- Date: 2026-10-07
- Mode: WHITEBOX, static read-only. No app execution, no SSH connections, no dynamic testing.
- Scope: src-tauri/src/lib.rs, src-tauri/src/main.rs, src/main.ts, index.html, src-tauri/tauri.conf.json, src-tauri/capabilities/default.json, src-tauri/Cargo.toml, package.json, .github/workflows/build-windows.yml. Everything else out of scope (observations only).
- Confidence ceiling: static-only analysis ⇒ at best MEDIUM confidence per finding.

## Findings (incremental log)

### F-1 — ssh arg option-injection via unvalidated `host` (MEDIUM) — CONFIRMED (static)
- Location: src-tauri/src/lib.rs:305-306 (`CommandBuilder::new("ssh"); cmd.arg(&host)`); host originates from src/main.ts:201 (`invoke("pty_spawn", { host, ... })`) ← main.ts:68 `openTerminal(h.name)` ← `read_ssh_config` output (lib.rs:185, `h.patterns.first()`), i.e. the first token of a `Host` line in ~/.ssh/config; also settable to any string via `save_host` (lib.rs:207-210 only checks non-empty).
- Analysis: portable-pty's `CommandBuilder` uses fork/execvp (unix) / CreateProcess argv (windows) — the value does NOT pass through a shell ⇒ classic `; $( )` shell injection is not reachable (see F-2). BUT the raw string is placed as ssh's first positional argument. Any value beginning with `-` is parsed by OpenSSH as an option, not a destination. A config line such as:
  ```
  Host -oProxyCommand=sh -c calc
  ```
  renders as a clickable host named `-oProxyCommand=sh` in the sidebar; clicking spawns `ssh -oProxyCommand=sh -c calc` — ssh runs ProxyCommand through the user's shell ⇒ arbitrary local command execution as the user. Same result for any hostile content reaching the config file (dotfiles sync, provisioning tools, a pasted raw-config save via `write_config_raw`, or programmatic `save_host` with name `-oProxyCommand=...`).
- Repro (static trace): 1) put `Host -oProxyCommand=touch /tmp/pwned` in ~/.ssh/config; 2) restart app; 3) click the host; code path main.ts:68 → main.ts:201 → lib.rs:306 yields argv `["ssh", "-oProxyCommand=touch", "/tmp/pwned"]` (split_whitespace at lib.rs:52-56 makes "touch" the alias — the option itself is still consumed by ssh, which is the dangerous part).
- Counterevidence (strongest case against): the trust boundary is the user's own ~/.ssh/config, which the user could equally put a `ProxyCommand` into directly — no privilege gained; attacker must already control the config file or the renderer. UI path additionally requires a click.
- Verdict: CONFIRMED (static) — code path fully traced; dynamic PoC prohibited by WHITEBOX mandate. Realistic severity MEDIUM (defense-in-depth missing at a real trust boundary: config files are commonly synced/provisioned, not hand-typed).
- Recommendation: in pty_spawn pass `--` before the host (`ssh -- <host>` is supported by OpenSSH getopt) and reject names not matching `^[A-Za-z0-9._@-]+$` in save_host; do the same validation in the frontend.

### F-2 — Shell injection via pty_spawn — RULED_OUT
- Location: src-tauri/src/lib.rs:305-308.
- Control that blocks every reachable path: portable-pty `CommandBuilder` never invokes a shell — on unix it fork/execvp's the binary directly with the argv array (portable-pty 0.8 ssh child code, exec via `execvpe`), on Windows it uses CreateProcess with the argument vector, not cmd.exe. Metacharacters (`;`, `$(`, backticks, `&&`) therefore reach ssh as inert argument text, never as shell syntax. No `.shell(true)`-equivalent API exists in portable-pty.

### F-3 — HOSTERM_CONFIG / ~/.ssh/config path handling — RULED_OUT (priv-esc) + INFO
- Location: src-tauri/src/lib.rs:32-38 (`config_path()`), used by read_ssh_config:180, save_host:211, delete_host:249, read_config_raw:262, write_config_raw:267-268.
- Analysis: the env var is consumed verbatim as an absolute path. There is no path-joining of untrusted input, no `..` handling issue — whoever sets HOSTERM_CONFIG already controls the process environment and hence the process. Path traversal is not reachable from the webview (frontend cannot set env vars; commands take content, never a path).
- Symlink: `std::fs::write` (lib.rs:146) follows an existing symlink at the target path — writing goes through e.g. a ~/.ssh/config symlink to elsewhere. Running as the unprivileged user, this cannot escalate; it is standard symlink-through behavior.
- TOCTOU: read-modify-write cycle (lib.rs:212 read → lib.rs:244 write) is unsynchronized with external editors; a concurrent change between read and write is silently clobbered. Integrity-only, INFO, accepted for a single-user desktop tool.
- Verdict: RULED_OUT for traversal/privilege escalation (control: process-env threat model, same-user execution, no attacker-reachable path input); INFO note on symlink-follow and read-write TOCTOU.

### F-4 — Config write safety: non-atomic write, unix-only 0600 — LOW — CONFIRMED (static)
- Location: src-tauri/src/lib.rs:142-153 (`write_config_file`).
- (a) Partial-write/corruption: `std::fs::write` truncates then writes in place; crash/power-loss mid-write leaves a truncated ~/.ssh/config. No temp-file + rename. CONFIRMED by code (integrity risk, MEDIUM-impact data loss for user's ssh config, LOW likelihood).
- (b) Permissions: 0600 applied only under `#[cfg(unix)]` (lib.rs:147-151); on Windows the file inherits default user-ACL — acceptable since keys live in separate files, INFO. On unix, a *newly created* file briefly has umask perms (typically 0644) between create (fs::write) and chmod — but a new file contains no secrets yet and existing files keep their inode perms; INFO.
- (c) Arbitrary clobber: `write_config_raw` writes ONLY to `config_path()` (lib.rs:268). The path cannot be influenced per-call ⇒ RULED_OUT arbitrary-file clobber; scope is HOSTERM_CONFIG env or ~/.ssh/config, both caller-controlled by definition.
- Recommendation: write to `path.with_extension("tmp")` then `fs::rename` (atomic on same filesystem), chmod before rename; on unix create with `OpenOptions.mode(0o600)`.

### F-5 — Parser robustness: panics / unbounded memory — RULED_OUT
- Location: src-tauri/src/lib.rs:40-140 (parse_config, serialize_config, get_opt, set_opt), save_host:215-243, delete_host:248-259, read_ssh_config:179-204.
- Analysis: parsing is a single linear pass over `text.lines()`; all allocations (Vec/String) are proportional to input size — no recursion, no per-iteration growth, no unbounded memory beyond input file size. `splitn(2, ...)` bounds splitting. Panic candidates checked: `hb.patterns[0] = ...` at lib.rs:225 is guarded by the `is_empty()` branch at 222; all other indexing uses `.first()` with `unwrap_or`/`unwrap_or_default` (185, 220, 254). `unwrap_or("")` on `split_whitespace().next()` (47) is total. `eq_ignore_ascii_case` is total. A pathological config (e.g. `Host` with no patterns) yields empty-name entries — cosmetic only. Malicious config content cannot cause worse than bad UI output.
- One INFO: `save_host`/`set_opt` write values verbatim into the serialized file (lib.rs:96-103); a value containing `\n` (reachable only programmatically, not through single-line `<input>` fields after `.trim()`) could splice extra directives into ~/.ssh/config — config self-corruption, not command exec.

### F-6 — Tauri capabilities minimal, CSP null — LOW hardening gap — CONFIRMED (static)
- Locations: src-tauri/capabilities/default.json:6-9 (only `core:default`, `core:event:default` — good, no fs/shell/opener permissions exposed); src-tauri/tauri.conf.json:24 (`"csp": null`).
- Analysis: capability surface is as narrow as it gets for this app — RULED_OUT over-broad capabilities. `core:event:default` is redundant (already inside `core:default`) — cosmetic.
- CSP null: the renderer loads only local bundled assets and the app has no `innerHTML` sinks with unescaped data (all host strings pass through `esc()` at main.ts:63/75-79 and error paths use `textContent`, main.ts:113/146) — no XSS path found. But with CSP null there is zero mitigation depth: any future XSS gains full IPC (`pty_spawn`, `write_config_raw` = arbitrary config content, i.e. foothold to F-1). `withGlobalTauri: true` (tauri.conf.json:13) additionally exposes `window.__TAURI__` to any injected script.
- Verdict: CONFIRMED as hardening gap (not a directly exploitable vuln). Recommendation: set e.g. `"csp": "default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:"` and drop `withGlobalTauri`.

### F-7 — GH Actions: token-free but actions unpinned — LOW — CONFIRMED (static)
- Location: .github/workflows/build-windows.yml.
- (a) Token exposure: none. No `GITHUB_TOKEN` passed to any step, no secrets referenced, artifact upload (lines 41-47) and release step (49-55) use runner defaults. `softprops/action-gh-release@v2` gets default `GITHUB_TOKEN` implicitly.
- (b) Permissions: top-level `permissions: contents: write` (lines 13-14) — write is needed for the release step; no pull-requests/packages/id-token grants, no job-level shrink. Acceptable, borderline least-privilege (could be job-scoped, INFO).
- (c) Pinning: ALL actions float on mutable tags, not commit SHAs — actions/checkout@v4 (line 20), actions/setup-node@v4 (23), dtolnay/rust-toolchain@stable (28), swatinem/rust-cache@v2 (31), actions/upload-artifact@v4 (42), softprops/action-gh-release@v2 (51). A compromised/redirected upstream tag executes in this workflow with `contents: write` on tag push. CONFIRMED as supply-chain exposure.
- (d) Trigger: `push: tags v*` + `workflow_dispatch` (7-11) — no pull_request_target, no untrusted PR code execution. RULED_OUT PR-based injection.
- Recommendation: pin all six actions to full commit SHAs; scope `permissions: contents: write` to the job.
